# Phase 14 contract: Bangladesh delivery and cash on delivery

**Status: built (2026-11-24).** Choices made where this page left something open are in the implementation notes (backend, storefront, admin) at the end; how it works for staff is in [docs/BANGLADESH.md](../BANGLADESH.md).

Decided by the user (2026-11-23): make delivery work the way Bangladeshi online shops do. Free: no outside account. Keeps the conventions of phases 1 to 13 (`snake_case`, money as 2-decimal strings in the store currency, `{ data }`, Laravel 422 errors, `can.admin:<key>`, audit entries, emails through the template system in the customer's language, the sign-in service (BFF) in front of every browser call, English and Bangla for every shopper-facing text, the DummyJSON demo mode working). **Nothing changes for non-Bangladesh addresses or for the current defaults**: Bangladesh features switch on per address (country `BD`) and per setting, so every existing test and browser suite keeps passing.

## 1. Bangladesh places (data)

- Source: `backend/database/data/bd-geo/` (nuhil/bangladesh-geocode, MIT, licence and README kept there): 8 divisions, 64 districts, 495 upazilas (English + Bangla names), 12 city corporations, 1,349 post offices with postcodes; metro **thanas** (`link_method: "metro_thana"`) have English names only.
- Tables `bd_divisions` (id, name, bn_name), `bd_districts` (id, division_id, name, bn_name), `bd_areas` (id, district_id, kind `upazila|thana`, name, bn_name, city_corporation null, postcodes json): one row per upazila, plus one per distinct metro thana (per district/city corporation) from the postcodes file, with **Bangla thana names written by BuyNest** (`bn_name`; listed in `docs/BANGLADESH.md` for review by a Bangla speaker). A seeder (`php artisan db:seed --class=BangladeshPlacesSeeder`, idempotent, also run by a migration) loads them; ids are the dataset's.
- Public, cached API: `GET /api/v1/places/bd/divisions`, `GET /api/v1/places/bd/districts?division=`, `GET /api/v1/places/bd/areas?district=` → `{ data: [{ id, name (in the request language), name_en, name_bn, kind?, postcodes? }] }`, ordered by the name in the request language. Cache headers like the catalog.

## 2. Bangladesh addresses and mobile numbers

- When `country` is `BD`, checkout addresses, the address book (phase 6), admin-created orders and customer/admin address forms use: **division_id, district_id, area_id** (all required; checked to belong together), `line1` (house/road/village, required), `line2` (optional), `postal_code` (optional for BD, 4 digits when given; suggested from the area), `phone` (required). `city` and `state` are filled by the server from the district and division names (English) so existing documents, emails and exports keep working; the address keeps the ids and shows names in the reader's language where the UI renders it.
- **Mobile numbers:** Bangladeshi mobiles accept `01XXXXXXXXX`, `+8801XXXXXXXXX`, `8801…`, with spaces/dashes; valid operator prefixes `013–019`; stored as `+8801XXXXXXXXX`. Clear 422 messages in both languages. Other countries keep the phase 1 rule.
- Settings: `store.default_country` (default stays as today; a Bangladeshi store sets `BD`), and `BD` can be added to `allowed_countries` like any country. `GET /api/v1/store` adds `default_country`.
- Storefront: when the country is Bangladesh the address form shows Division → District → Area (upazila/thana) selects (names in the shopper's language, searchable on phones, keyboard friendly), then house/road and optional postcode (pre-filled when the area has exactly one). Saved addresses show the Bangladesh format. Demo mode: unchanged.

## 3. Delivery zones and charges

- `delivery_zones`: id, code (unique, e.g. `inside_dhaka`, `dhaka_suburbs`, `outside_dhaka`), name, bn_name, position, is_active; `delivery_zone_places`: zone_id + one of district_id / area_id (an area match beats a district match beats the fallback zone). Seeded (rows only, **no prices**): **Inside Dhaka** = the thanas of Dhaka North and South city corporations; **Dhaka suburbs** = the rest of Dhaka district plus Gazipur, Narayanganj; **Outside Dhaka** = the fallback for every other place in Bangladesh. Staff can edit zones and their places (`settings.edit`).
- Charges reuse phase 10 **shipping table rates**: `shipping_rates` gets nullable `zone_code`; a BD address matches rows with its zone first, then country `BD`, then `*` (existing weight/subtotal bands still apply). Each zone rate row can also carry `eta_days_min`, `eta_days_max` (shown as "Delivery in 1–2 days" / "১–২ দিনে ডেলিভারি"). No zone rows → today's behaviour.
- Cart validation, checkout and admin-created orders answer the methods, prices and ETA for the address's zone; the order stores `delivery_zone_code` and the area ids.
- Storefront checkout shows the zone name and ETA under each method; cart shows "Delivery charge is calculated from your area" until an area is chosen.

## 4. Cash on delivery the Bangladeshi way

Settings (Settings → Payment methods → Cash on delivery, `settings.edit`): `cod.max_order_total` (null = no limit), `cod.fee` (added to COD orders, default 0), `cod.advance` (`none` | `delivery_charge`: the shopper pays the delivery charge online first, the rest on delivery; default `none`), `cod.zones` (zone codes where COD is offered; empty = everywhere), `cod.require_confirmation` (bool, default false).

- COD is offered only when allowed for the zone and the total is within the limit; otherwise the checkout explains why (both languages) and the API refuses with 422 `payment_method`.
- **Advance delivery charge:** with `cod.advance = delivery_charge`, placing a COD order opens an **SSLCommerz** session (phase 12, through the same gateway and validation) for the delivery charge (plus COD fee) only. The order is `pending_payment` until the advance is validated, then becomes `processing` with `payment_status: "partially_paid"`, `advance_paid` (money), and `cod_due` (the rest, collected on delivery). Unpaid advances expire like other SSLCommerz attempts (cancel + restock once). Needs SSLCommerz enabled; otherwise the setting can't be turned on (422 with an explanation). Refunds return the advance through SSLCommerz first.
- **Collecting the cash:** marking a COD order delivered asks staff to confirm the amount collected; the order becomes `paid` and is invoiced (OrderDocuments) with the cash line and the advance line. A short collection is recorded with a note and leaves `cod_due` > 0 (`payment_status: "partially_paid"`), with an admin notification.
- **Phone confirmation:** with `cod.require_confirmation`, new COD orders get `confirmation_status: "pending"` (`confirmed|unreachable|cancelled`), `confirmation_attempts`, and a log (`order_confirmation_logs`: admin, outcome, note, time). Admin page **Sales → To confirm** (`orders.edit`): oldest first, the customer's mobile as a `tel:` link, previous orders count and returns, buttons Confirmed / Couldn't reach / Cancel order (with reason; cancelling restocks and emails the customer), notes. Unconfirmed orders can't be shipped (422 with a clear message) unless staff override with a reason (audited). The customer's order page shows "We'll call you to confirm" / "Confirmed".

## 5. Courier-ready orders

- **Packing slips:** `GET /api/admin/v1/orders/{number}/packing-slip.pdf` and bulk (`POST /api/admin/v1/orders/packing-slips` with numbers → one PDF, max 100), `orders.view`: big order number, recipient, mobile, full Bangladesh address (both languages when the order is Bangla), items and quantities (no prices), COD amount to collect in large type, delivery zone, note. dompdf like phase 10/13 (Bangla font).
- **Courier CSV:** `GET /api/admin/v1/orders/export/courier.csv?numbers=…` or by filter (`orders.view`): `invoice, recipient_name, recipient_phone, recipient_address, district, area, cod_amount, weight_kg, note`, UTF-8 with BOM (opens in Excel with Bangla). Column presets for specific couriers are **not** claimed this phase (their formats need checking with each courier); `docs/BANGLADESH.md` explains how to map the columns.
- Admin orders grid: filters for delivery zone, COD, confirmation status; bulk actions Packing slips, Courier CSV.

## 6. Emails and texts

- Order confirmation and shipping emails show the Bangladesh address format, delivery zone and ETA, the COD amount to keep ready, and the advance paid (both languages). New template `cod_confirmed` ("We've confirmed your order") is sent when staff confirm, and the existing cancel email covers cancellations at confirmation.
- Every new shopper-facing text in English and Bangla (catalog parity test from phase 13 must stay green).

## Implementation notes — backend

**Status: done (2026-11-24).** These are the exact routes and shapes the backend answers. Tests: `tests/Feature/BangladeshAddressTest.php`, `tests/Feature/CashOnDeliveryTest.php` (full suite 550 green). How it works for staff: `docs/BANGLADESH.md`.

### Data (§1)

- Tables `bd_divisions` (id, name, bn_name), `bd_districts` (id, division_id, name, bn_name), `bd_areas` (id, district_id, kind `upazila|thana`, name, bn_name, city_corporation (English name, thanas only), postcodes JSON list of 4-digit strings). Upazila ids are the dataset's (1–495). Metro thanas get ids **1001–1018**, in the order they first appear in `postcodes.json` (18 distinct metro thanas: 17 in Dhaka North/South, 1 in Khulna). Upazila postcodes come from the post offices linked to them.
- `php artisan db:seed --class=BangladeshPlacesSeeder` (idempotent: upserts by id); migration `2026_11_23_000200_create_bangladesh_places` runs it. Zones: migration `2026_11_23_000210_create_delivery_zones` seeds the three zones and their places (`DeliveryZonesSeeder`, idempotent: only adds what is missing, never prices).

### Places API (public, `throttle:api`, `Cache-Control: public, max-age=86400`, `Vary: Accept-Language`)

- `GET /api/v1/places/bd/divisions` → `{ data: [{ id, name, name_en, name_bn }] }`
- `GET /api/v1/places/bd/districts?division=<id>` (division optional: all 64 without it) → `{ data: [{ id, division_id, name, name_en, name_bn }] }`
- `GET /api/v1/places/bd/areas?district=<id>` (district **required**, 422 `district`) → `{ data: [{ id, district_id, name, name_en, name_bn, kind: "upazila"|"thana", city_corporation: string|null, postcodes: ["1207", …] }] }`
- `name` is in the request language (Accept-Language / phase 13 rules); lists are ordered by `name` in that language. Unknown division/district → `{ data: [] }`.

### Bangladesh addresses (§2)

- A Bangladesh address is one whose `country` is `Bangladesh` or `BD` (any case). `BD` is stored as the store's spelling in `allowed_countries` (normally `Bangladesh`).
- **Structured rules** apply to a Bangladesh address when it sends any of `division_id`/`district_id`/`area_id`, or when the setting `checkout.default_country` is Bangladesh. (So old clients sending a free-text Bangladesh address in a non-Bangladesh store keep working.) Structured: `division_id`, `district_id`, `area_id` required integers that exist and belong together (422 on `<prefix>.district_id` "The district isn't in the chosen division." / `<prefix>.area_id` "The area isn't in the chosen district."), `line1` required, `line2` optional, `postal_code` optional, 4 digits when given (`<prefix>.postal_code` "Enter a 4-digit postcode."), `city` and `state` are not required and are **overwritten** with the district and division English names.
- Stored order address (checkout, admin-created orders): the 8 usual keys, plus for structured Bangladesh addresses `division_id`, `district_id`, `area_id`, `area` (the area's English name). Non-Bangladesh addresses keep exactly the 8 keys.
- Address book (store `/api/v1/me/addresses`, admin `/customers/{id}/addresses`): same rules; `postal_code` optional for structured BD; the address answer adds `division_id`, `district_id`, `area_id` (null when not set).
- **Mobile numbers:** for a Bangladesh address (order `phone` follows the shipping address; address book `phone` its own address; admin guest phone follows the shipping address) `01XXXXXXXXX`, `8801XXXXXXXXX`, `+8801XXXXXXXXX`, `008801…`, with spaces/dashes/dots/brackets, are stored as `+8801XXXXXXXXX`. For structured BD addresses the number must be a Bangladeshi mobile (`+8801[3-9]` + 8 digits): 422 on `phone` "Enter a Bangladeshi mobile number, for example 01712 345678." (Bangla: "সঠিক একটি বাংলাদেশি মোবাইল নম্বর দিন, যেমন ০১৭১২ ৩৪৫৬৭৮।"). Other countries: phase 1 rule unchanged.
- Settings: `checkout.default_country` (null by default = today's behaviour; a name from `allowed_countries`, ISO code accepted and converted, 422 when not allowed). `GET /api/v1/store` adds `default_country`.

### Delivery zones and rates (§3)

- `delivery_zones`: id, code (unique, `^[a-z0-9_]{2,40}$`), name, bn_name, position, is_active, **is_fallback** (exactly one zone may be the fallback; seeded: `outside_dhaka`). `delivery_zone_places`: id, zone_id, district_id | area_id (each district / area belongs to at most one zone).
- Matching (`DeliveryZones::zoneFor(area_id, district_id)`): active zone holding the area → active zone holding the district → the active fallback zone → null. Only structured Bangladesh addresses have a zone.
- Seeded: `inside_dhaka` "Inside Dhaka" / "ঢাকার ভেতরে" (the 17 Dhaka metro thanas), `dhaka_suburbs` "Dhaka suburbs" / "ঢাকার আশপাশ" (districts Dhaka 47, Gazipur 41, Narayanganj 43), `outside_dhaka` "Outside Dhaka" / "ঢাকার বাইরে" (fallback). No prices.
- `shipping_rates` adds `zone_code` (nullable), `eta_days_min`, `eta_days_max` (nullable ints 0–60, min ≤ max). A row with a `zone_code` matches only an address in that zone (its `country` is ignored); rows match in this order: zone rows, then the exact country, then `*` (then position, id). Weight/subtotal bands still apply. No zone rows → exactly the phase 10 behaviour. Admin rate API (`/api/admin/v1/shipping-rates…`) accepts and answers `zone_code`, `eta_days_min`, `eta_days_max` (422 `zone_code` when the zone doesn't exist); CSV export/import add the columns `zone_code,eta_days_min,eta_days_max` at the end (import: optional columns).
- Admin zones API: `GET /api/admin/v1/delivery-zones` (`settings.view`) → `{ data: [Zone] }`, `POST /api/admin/v1/delivery-zones`, `PATCH /api/admin/v1/delivery-zones/{id}`, `DELETE /api/admin/v1/delivery-zones/{id}` (`settings.edit`; delete refused with 422 `zone` for the fallback zone or a zone used by shipping rates or the `cod.zones` setting), `GET /api/admin/v1/delivery-zones/match?area_id=&district_id=` (`settings.view`) → `{ data: Zone|null }`. Zone: `{ id, code, name, bn_name, position, is_active, is_fallback, districts: [{ id, name, bn_name }], areas: [{ id, name, bn_name, district_id, district_name }], rates_count }`. Body (POST all, PATCH partial): `{ code, name, bn_name, position?, is_active?, is_fallback?, district_ids?: int[], area_ids?: int[] }` (the lists replace the zone's places; a place in another zone → 422 `district_ids.N` / `area_ids.N` "… is already in zone X."). Audit `delivery_zone.created|updated|deleted`.
- Cart validation `POST /api/v1/cart/validate` accepts `area_id`, `district_id` (optional ints, with `country`) and `payment_method` (optional). Answer adds `delivery_zone: { code, name, name_en, name_bn } | null`, each `shipping_options[]` adds `eta_days_min`, `eta_days_max` (null unless the table rate row has them) and `zone_code` (the matched row's, or null); `eta` is then "Delivery in 1–2 days" / "Delivery in 1 day" (Bangla "১–২ দিনে ডেলিভারি", "১ দিনে ডেলিভারি"). `totals` adds `cod_fee`. Answer adds `cod` (see §4).
- Orders store `delivery_zone_code`, `delivery_eta_min`, `delivery_eta_max`; the area ids are in `shipping_address`.

### Cash on delivery (§4)

- Settings group `cod` (`GET/PATCH /api/admin/v1/settings`, `settings.edit`): `max_order_total` (money string or null), `fee` ("0.00"), `advance` (`none`|`delivery_charge`), `zones` (zone codes, [] = everywhere), `require_confirmation` (bool). Stored as `cod_max_order_total`, `cod_fee`, `cod_advance`, `cod_zones`, `cod_require_confirmation`. `advance: delivery_charge` → 422 `cod.advance` "Advance delivery charge needs SSLCommerz: set SSLCOMMERZ_STORE_ID and SSLCOMMERZ_STORE_PASSWORD and use the store currency BDT." when SSLCommerz isn't enabled. Unknown zone codes → 422 `cod.zones.N`.
- `GET /api/v1/store` adds `cod: { fee, max_order_total, advance, zones, require_confirmation }`.
- Cart/checkout `cod` object: `{ available: bool, reason: null|"zone"|"limit"|"area_required", message: string|null (request language), fee, max_order_total, advance: "none"|"delivery_charge", advance_amount }`. `advance_amount` = shipping + COD fee when `advance` is `delivery_charge` (and SSLCommerz is on), else "0.00". `area_required` only when `cod.zones` is set and the address has no zone yet.
- COD fee is added to the total when `payment_method` is `cod` (`totals.cod_fee`; tax isn't charged on it). The limit compares the total including the fee.
- Placing a COD order that isn't allowed → 422 `payment_method` with the message ("Cash on delivery isn't available in your area." / "Cash on delivery is available for orders up to :amount.").
- Orders add: `cod_fee`, `advance_amount`, `advance_paid`, `cod_due` (cash still to collect), `cod_collected`, `confirmation_status` (null|pending|confirmed|unreachable|cancelled), `confirmation_attempts`, `confirmed_at`. `payment_status` gains `partially_paid`.
- Advance: the order is `pending_payment`, `payment` works like an SSLCommerz order (POST /orders answers `data.payment.url`; Pay now; IPN/return; expiry cancels and restocks once) for `advance_amount` only. Validated → invoice for the advance amount, `status: processing`, `payment_status: partially_paid` (or `paid` when nothing is left), `advance_paid` set. Refunds send up to the advance (minus what was already refunded through SSLCommerz) back through SSLCommerz first; the rest is a manual refund.
- Collection: `PATCH /api/admin/v1/orders/{number}` accepts `collected_amount` (money, 0 ≤ amount ≤ cod_due) and `collection_note` (required when short) together with `status: "delivered"` or on an already delivered/shipped COD order. Full → invoice for the rest (note lists cash and advance), `payment_status: paid`, `cod_due: "0.00"`. Short → an invoice for what was collected (when > 0), `payment_status: partially_paid`, `cod_due` = the rest, admin notification `cod_short_collection`. 422 `collected_amount` when more than due / not a COD order / nothing due. Without `collected_amount` delivered works as before (nothing is invoiced).
- Confirmation (`cod.require_confirmation`): new COD orders get `confirmation_status: "pending"`. `GET /api/admin/v1/orders/to-confirm?per_page=` (`orders.edit`): pending and unreachable, not cancelled, oldest first → `{ data: [ToConfirm], meta, links }` with ToConfirm `{ number, placed_at, status, payment_status, currency, grand_total, cod_due, advance_paid, customer_name, phone, tel_url, email, address (one line), delivery_zone: {code,name}|null, confirmation_status, confirmation_attempts, last_note, last_attempt_at, previous: { orders, delivered, cancelled, returns } }`. `POST /api/admin/v1/orders/{number}/confirmation` (`orders.edit`) `{ outcome: confirmed|unreachable|cancelled, note?, reason? (required for cancelled), notify_customer? (default true) }` → `{ data: AdminOrderResource }`; confirmed emails `cod_confirmed`; cancelled cancels (restock, `order_status` cancelled email). 422 `order` when the order isn't waiting for confirmation. Logs: `order_confirmation_logs` (id, order_id, admin_id, outcome, note, created_at).
- Shipping an unconfirmed COD order (pending/unreachable) → 422 (`order` on the shipment endpoint, `status` on the PATCH shortcut, `skipped` reason in bulk) "This cash on delivery order hasn't been confirmed by phone yet. Confirm it first, or ship it anyway with a reason." unless `confirmation_override` (string, 3–500) is sent to `POST /orders/{number}/shipments` or the PATCH; the override is logged (`order_confirmation_logs` outcome `override`) and audited (`order.confirmation_overridden`).
- `OrderResource` (store) adds `delivery: { zone_code, zone_name, eta_days_min, eta_days_max, eta }`, `cod: { fee, advance_amount, advance_paid, cod_due } | null` (null for non-COD orders), `confirmation_status`. `AdminOrderResource` adds the same plus `cod.collected`, `confirmation: { status, attempts, confirmed_at, logs: [{ id, outcome, note, admin_name, created_at }] }` (logs on the detail answer).
- Admin grid `GET /api/admin/v1/orders` (and export.csv) filters: `delivery_zone` (code), `cod` (bool: payment method cod or not), `confirmation_status`.

### Courier-ready orders (§5)

- `GET /api/admin/v1/orders/{number}/packing-slip.pdf` and `POST /api/admin/v1/orders/packing-slips { numbers: [1..100] }` (`orders.view`) → `application/pdf` attachment (`packing-slip-BN-100001.pdf` / `packing-slips-YYYY-MM-DD.pdf`, one page per order in the order given; 422 `numbers` "Orders not found: …" when any is unknown). Page: order number (large), date + shipping method, zone (English / Bangla) + ETA, recipient, mobile (large), address in English (plus a Bangla column when the order's locale is `bn`), "Collect in cash (COD)" amount (large; "PREPAID: collect nothing" otherwise) and "Advance paid online", items (name, variant, SKU, quantity; no prices). Labels are English. The JSON `GET …/packing-slip` stays unchanged.

## Implementation notes — storefront

**Status: done (2026-11-24).** Follows "Implementation notes — backend" above.

### When the Bangladesh features are on

- The Division → District → Area form, the Bangladeshi mobile check and the cart's area note are on when `GET /store` `default_country` is Bangladesh (`BD` or the name) — exactly when the API applies its structured Bangladesh rules — or when the store answer says `bd_addresses: true`. Then a Bangladesh address uses the new form and every other country the old fields. Without that setting (and in the demo), Bangladesh keeps the free-text city/state fields, so phase 12/13 tests and browser suites (taka.mjs, bangla.mjs) are unchanged. ### Sign-in service (BFF)
