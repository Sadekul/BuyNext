# Phase 12 contract: taka (BDT) as the store currency, and bKash / Nagad / local cards through SSLCommerz

**Status: built (2026-11-19).** Choices made where this page left something open are in the implementation notes (backend, storefront, admin) at the end.

Decided by the user (2026-11-19): add **SSLCommerz** (bKash, Nagad, Rocket, Upay, local and international cards, internet banking on one hosted page) and make the store **charge in taka**. Keeps the conventions of phases 1 to 11 (`snake_case`, money as 2-decimal strings, `{ data }`, Laravel 422 errors, `can.admin:<key>`, audit entries, emails through the template system, the sign-in service (BFF) in front of every browser call, the API locked to the store in production, the DummyJSON demo mode unchanged). Built and tested with a **stand-in** SSLCommerz server, like Stripe (phase 8) and PayPal (phase 10); no real account is needed until going live.

## 1. One store currency, chosen by configuration

Today the currency is hard-coded as USD in several places (`config/buynest.php` `store.currency`, `STRIPE_CURRENCY`, the admin's `format.js`, the storefront formatter). Prices in the database have no currency of their own, so the store currency is a **deployment setting**, not an admin toggle (changing it changes what every stored price means; see §2).

- `.env`: `BUYNEST_CURRENCY` (ISO 4217, default `USD`), read into `config('buynest.store.currency')`. Supported: `USD`, `BDT` (others may be listed in a small table with symbol and decimals; BDT = `৳`, 2 decimals, symbol before the amount with no space: `৳1,250.00`).
- Stripe charges in the store currency (lower-case code); `STRIPE_CURRENCY` is removed or only used when set explicitly (document which). Stripe supports BDT.
- **PayPal does not support BDT.** When the store currency isn't one PayPal accepts, PayPal is off: `GET /api/v1/store` answers `paypal_payments: "unavailable"`, the storefront hides it, placing a PayPal order is refused (422 `payment_method`), and the admin's payment settings explain why.
- `orders.currency` (char 3, new): set at placement to the store currency; existing orders are back-filled with `USD`. Invoices, credit memos, PDFs, emails, order pages (customer and admin), reports and exports format each order's money **in that order's currency**, so old orders stay correct after a switch. Gift cards already have `currency`; a card can only pay for orders in its own currency (422 otherwise).
- `GET /api/v1/store` adds `currency: { code, symbol, decimals }` (the store currency); `currencies.base` (phase 11) equals it. Display currencies (phase 11) stay relative to the store currency (with BDT as the base, staff could offer USD for display).
- **Storefront and admin:** every money formatter reads the store currency from the store settings (storefront: `useStoreSettings`; admin: the store settings it already loads, or `GET /api/admin/store-info`-like data if needed) instead of a hard-coded USD. Until settings load, format with USD (today's behaviour) so nothing flashes errors. The phase 11 "You'll be charged … USD" note uses the store currency's code. Order and invoice views use the order's `currency` when present.
- Emails, PDFs and the dev mailbox show `৳` amounts correctly (DejaVu Sans in the PDFs already covers `৳`; check it renders).

## 2. Switching an existing store's prices: `php artisan buynest:currency:convert`

- `php artisan buynest:currency:convert BDT --rate=110 [--dry-run] [--round=1|5|10|0.01]` multiplies every **stored price-like amount** by the rate and rounds (default to whole taka, `--round=1`): products' price and special prices, variant prices and price adjustments, gift card product amounts and limits, catalog and cart rule fixed amounts and thresholds, coupons' fixed amounts and minimum subtotals, settings (shipping flat prices, free-shipping threshold, gift card limits, reward `point_value`), shipping table rate prices and subtotal bands, unused gift card balances (with a transaction note). It does **not** touch orders, invoices, credit memos or history.
- Refuses to run unless `BUYNEST_CURRENCY` already equals the target (so the code and the data change together), and refuses a second run for the same target (records the conversion in a `currency_conversions` table: from, to, rate, rounding, admin/CLI, counts, created_at). `--dry-run` prints counts and a few before/after examples and changes nothing. One transaction; audited.
- Documented step by step in `docs/CURRENCY.md` (back up first with `buynest:backup`, set `BUYNEST_CURRENCY=BDT`, run with `--dry-run`, run for real, check the shop, clear caches).
- The local dev database stays in USD (the browser suites expect it); tests cover BDT with their own data.

## 3. SSLCommerz payments

Same design as Stripe and PayPal: a small gateway class with the Laravel HTTP client, no SDK, a stand-in server for tests.

- `.env`: `SSLCOMMERZ_STORE_ID`, `SSLCOMMERZ_STORE_PASSWORD`, `SSLCOMMERZ_MODE` (`sandbox`|`live`), `SSLCOMMERZ_API_URL` (only for local tests; defaults `https://sandbox.sslcommerz.com` / `https://securepay.sslcommerz.com`). Enabled when id and password are set **and** the store currency is BDT (SSLCommerz also accepts USD, but this phase targets BDT; document). Otherwise `GET /api/v1/store` answers `sslcommerz_payments: "manual"` (or `"unavailable"` when the currency isn't BDT) and orders with `payment_method: "sslcommerz"` are refused (422) unless manual mode is on (then they wait for staff like other manual methods).
- New payment method id **`sslcommerz`**, label "bKash, Nagad, cards (SSLCommerz)", in the store's payment methods and Settings → Payment methods (on/off like the others).
- `App\Services\Payments\SslCommerzGateway`:
  - **Create session:** `POST {api}/gwprocess/v4/api.php` (form-encoded) with `store_id`, `store_passwd`, `total_amount` (the amount due after points and gift card), `currency=BDT`, `tran_id` (unique per attempt: `<order number>-<n>`), `success_url`, `fail_url`, `cancel_url`, `ipn_url`, customer fields (`cus_name`, `cus_email`, `cus_add1`, `cus_city`, `cus_postcode`, `cus_country`, `cus_phone`; phone is required by SSLCommerz: use the address phone or the order phone, else a clear 422 asking for one), `shipping_method` (`YES` with ship_* fields, or `NO` for gift-card-only orders), `product_name` (first item names, truncated), `product_category`, `product_profile=general`, `num_of_item`, `value_a` = order number. Answer `{ status: "SUCCESS", GatewayPageURL, sessionkey }`; anything else → 502-style error, the order stays unpaid with "Pay now" available.
  - **Validate:** `GET {api}/validator/api/validationserverAPI.php?val_id=&store_id=&store_passwd=&format=json` → must answer `status` `VALID` or `VALIDATED`, `tran_id` of this order's current attempt, `currency_type`/`currency` `BDT`, and `amount` (or `currency_amount`) equal to the amount due (to the cent); `risk_level` `1` → keep the order **on hold** (payment status `review`, admin notification) instead of invoicing.
  - **Refund:** `GET {api}/validator/api/merchantTransIDvalidationAPI.php?bank_tran_id=&refund_amount=&refund_remarks=&refe_id=<credit memo number>&store_id=&store_passwd=&format=json` → `status: "success"` with `refund_ref_id` (stored on the credit memo as the provider reference); `"processing"` is accepted the same way and noted; anything else → 422, nothing saved (same as Stripe/PayPal refusals).
  - **Query by transaction:** `GET …/merchantTransIDvalidationAPI.php?tran_id=&store_id=&store_passwd=&format=json`, used by the expiry job and by "Check payment" in the admin.
- **The return trip:** SSLCommerz sends the shopper's browser back with a **form POST** to `success_url` / `fail_url` / `cancel_url`. These point at the store's sign-in service: `POST /api/payments/sslcommerz/return/{result}` (`success|fail|cancel`) reads the posted `tran_id`, `val_id`, `status`, forwards them to the API (`POST /api/v1/payments/sslcommerz/return`, with the shared key), and answers **303** to the confirmation page (`/order-confirmation/<number>?payment=success|failed|cancelled&provider=sslcommerz`). The API **never trusts the posted status**: on `success` it validates `val_id` server-side before marking anything paid. Same-site cookie note: the POST comes from SSLCommerz's domain, so it must not depend on the customer's session cookie (`SameSite=Lax` cookies aren't sent on cross-site POSTs); the order number travels in `value_a`/`tran_id` and the confirmation page reloads the order normally.
- **IPN:** `POST /api/v1/payments/sslcommerz/ipn` (through the store with the shared key, raw form body, like the Stripe/PayPal webhooks). Verified by calling the validation API with the posted `val_id` (not by trusting the posted fields; `verify_sign` may be checked too as an extra). Idempotent through `payment_events` (provider `sslcommerz`, event id `val_id` or `tran_id`+status). Marks paid if the return trip was missed; `FAILED`/`CANCELLED` IPNs only add a history note.
- **Paid** → invoice through `OrderDocuments` exactly like Stripe/PayPal (rewards earned, emails). Store `bank_tran_id`, `card_type` (e.g. `BKASH-BKash`, `NAGAD-Nagad`, `VISA-Dutch Bangla`), `card_brand`, `val_id` on the order's payment record; customer and admin order pages show "Paid with bKash (SSLCommerz)" using a friendly name from `card_type`.
- **Unpaid expiry:** like Stripe/PayPal (3 hours, scheduled): before cancelling, query by `tran_id`; if SSLCommerz says VALID/VALIDATED, record payment instead of cancelling. Cancel restocks once and returns points/gift card (phase 10/11 rules).
- **Pay now / payment links:** customer "Pay now" on an unpaid SSLCommerz order and the admin's payment link start a fresh attempt (`tran_id` suffix +1); older attempts' successes are still accepted if validated and the amount matches (then later attempts are ignored).
- Admin order page: provider SSLCommerz, method (bKash/Nagad/card), `bank_tran_id`, `val_id`, risk level, attempts, "Check payment" (`orders.edit`, queries by tran_id and records payment if found), refunds through SSLCommerz first.
- **CSP:** none needed (redirect only, no SSLCommerz script). The confirmation page must still work after a cross-site POST → 303.

## 4. Storefront

- Checkout lists **"bKash, Nagad or card (SSLCommerz)"** with the bKash/Nagad/card marks drawn as simple text badges (no third-party logos fetched from outside), and a note "You'll finish paying on SSLCommerz's secure page." Requires a phone number in the address (the address form already has phone: make it required only when SSLCommerz is chosen, with a clear message).
- Placing the order redirects to `GatewayPageURL`. The confirmation page handles `payment=success|failed|cancelled&provider=sslcommerz` like PayPal (polls the order a few times while the IPN may still be arriving; "Payment failed / cancelled: try again" with Pay now).
- Every price, total and email in taka when the store currency is BDT (via §1). Gift card amounts, free-shipping progress, shipping rates and reward point values follow the store currency.
- Demo mode: SSLCommerz isn't offered.

## 5. Admin

- Settings → Payment methods: SSLCommerz on/off, with status ("Live", "Sandbox", "Not configured: set SSLCOMMERZ_STORE_ID and SSLCOMMERZ_STORE_PASSWORD", "Needs the store currency BDT"), like Stripe/PayPal.
- Settings shows the store currency (read-only, with a link to `docs/CURRENCY.md`), and PayPal shows "Not available in BDT" when off for that reason.
- Order page, refunds, payment links, "Check payment" as in §3; reports and grids format each order's own currency (a mixed-currency period shows totals per currency, not a sum across currencies).
- All admin money formatting uses the store currency (or the order's currency) instead of a hard-coded USD.

## Permissions

No new keys: payment settings `settings.edit`, "Check payment" and payment links `orders.edit`, refunds as today.

## Implementation notes — backend

Written by the backend agent; this section is the source of truth for exact shapes. **Status: backend done** — every route below exists on the dev API's database (migrated; the dev DB stays in USD), full backend suite green: **499 tests** (474 existing, 8 of them with the new fields added to exact-shape expectations, + 25 new in `SslCommerzPaymentTest` (14) and `StoreCurrencyTest` (11)); `pint --test` clean; `composer audit` clean. Everything defaults to today's behaviour when `BUYNEST_CURRENCY` is unset (USD).

### Configuration (`backend/.env.example`)
- `BUYNEST_CURRENCY` (default `USD`) → `config('buynest.store.currency')` (upper case). Known formats (`config('buynest.currencies')`): `USD $`, `BDT ৳`, `EUR €`, `GBP £`, `INR ₹`, `CAD CA$`, `AUD A$`, all 2 decimals, symbol before the amount with no space, thousands separators: `৳1,250.00`, `-৳5.00`. An unknown code is written `XYZ 1,250.00`. Helper: `App\Support\Currency` (`store()`, `api()`, `format($amount, $code)`, `formatCents()`, `paypalAccepts()`, `sslcommerzAccepts()`).
- **`STRIPE_CURRENCY` is removed** (ignored if still set): Stripe charges in the order's currency, which is the store currency at placement (lower case, e.g. `bdt`).
- PayPal accepts `config('buynest.paypal.currencies')`: `USD EUR GBP CAD AUD JPY CHF SEK NOK DKK PLN CZK HUF NZD SGD HKD MXN ILS PHP TWD THB BRL MYR`. BDT and INR aren't in it → PayPal is **unavailable**. PayPal refunds / expiry checks of older PayPal orders still work after a switch (they only need the credentials).
- SSLCommerz: `SSLCOMMERZ_STORE_ID`, `SSLCOMMERZ_STORE_PASSWORD`, `SSLCOMMERZ_MODE` (`sandbox`|`live`, default sandbox), `SSLCOMMERZ_API_URL` (tests/stand-in only; default `https://sandbox.sslcommerz.com` / `https://securepay.sslcommerz.com`), `BUYNEST_SSLCOMMERZ_CALLBACKS_PER_MINUTE` (300, limiter `sslcommerz` per IP for return + IPN). New payments only when id + password are set **and** the store currency is BDT (SSLCommerz also takes USD, but this phase charges in BDT only: `config('buynest.sslcommerz.currencies') = ['BDT']`). Refunds and Check payment only need id + password.

### Placing orders (`POST /api/v1/orders`, admin `POST /api/admin/v1/orders`)
- `payment_method: "paypal"` in a BDT store → 422 `errors.payment_method` "PayPal doesn't accept BDT, so it isn't available in this store."; `sslcommerz` in a non-BDT store → "bKash, Nagad and cards (SSLCommerz) need the store currency BDT."; a method that's simply switched off keeps "Choose a payment method.".
- `payment_method: "sslcommerz"` without a phone → 422 `errors.phone` "SSLCommerz needs a phone number for the payment. Add one to place this order." (the storefront already requires `phone`, so this only bites admin-created orders for customers without one). The order's `phone` is what's sent as `cus_phone` (addresses have no phone field).
- Gift card in another currency → 422 `errors.gift_card_code` "This gift card is in USD, so it can't pay for an order in BDT." (cart/validate shows the same text as `gift_card_error`). New cards take the store currency.
- SSLCommerz online → **201** with `data.payment = { provider: "sslcommerz", url: <GatewayPageURL>, expires_at, paid_at: null, can_pay: true, method_label: null }` — send the browser to `url`. SSLCommerz refuses / can't be reached → `url: null, expires_at: null, error: "SSLCommerz could not start the payment (<reason>). Please try again in a moment."` (or "SSLCommerz is having trouble right now. …" / "SSLCommerz could not be reached. …"); the order stays `pending_payment`/`unpaid`, Pay now retries.
- Session fields sent (form-encoded to `{api}/gwprocess/v4/api.php`): `store_id, store_passwd, total_amount` (= `totals.amount_due`: grand total − points − gift card), `currency` (the order's, BDT), `tran_id` = `<order number>-<attempt>`, `success_url|fail_url|cancel_url` = `STOREFRONT_URL/api/payments/sslcommerz/return/success|fail|cancel`, `ipn_url` = `STOREFRONT_URL/api/payments/sslcommerz/ipn`, `cus_name/email/add1/add2/city/state/postcode/country/phone` (billing address, else shipping), `shipping_method` `YES` + `ship_*` (or `NO` for gift-card-only orders), `num_of_item`, `product_name` (item names, ≤255), `product_category` (`General` / `Gift card`), `product_profile=general`, `value_a` = order number, `value_b` = attempt.

### Orders (customer `OrderResource`, admin `AdminOrderResource`, grids, invoices, credit memos)
- New top-level `currency: "BDT"` on orders (customer + admin, detail + grid + lookup), invoices (`InvoiceResource`) and credit memos (`CreditMemoResource`, also inside the admin order). `USD` for every old order. Format every amount of the order with it.
- New payment status **`review`** (`Order::PAYMENT_STATUSES` = `unpaid, review, paid, partially_refunded, refunded`; admin grid filter `payment_status=review` works): SSLCommerz took the money but flagged it (`risk_level` 1). The order stays `pending_payment`, no invoice, a staff history note and a `payment_problem` admin notification ("Payment on hold for order BN-…"). Staff approve it with the existing mark-paid / create invoice (now allowed from `review`), or cancel it (and refund in SSLCommerz's panel). The customer can't Pay now ("This order's payment was received and is being checked.") or cancel it online. Dashboard to-do `orders_to_invoice` counts `review` too.
- `payment` adds **`method_label`** for everyone (null except SSLCommerz): from `card_type` → `"bKash"`, `"Nagad"`, `"Rocket"`, `"Upay"`, `"Visa card"`, `"Mastercard"`, `"American Express"`, `"Internet banking"`, else the part before `-`. Show "Paid with bKash (SSLCommerz)".
- Staff (`AdminOrderResource.payment`) also get **`sslcommerz`**: `null` for non-SSLCommerz orders, else `{ tran_id (latest attempt or the paid one), val_id, bank_tran_id, card_type, card_brand, card_issuer, risk_level ("0"|"1"|null), risk_title, attempts, mode: "sandbox"|"live", can_check: bool }` (`can_check`: configured, ≥1 attempt, payment `unpaid`/`review`, not cancelled). `reference` = `bank_tran_id`; `dashboard_url` = null.
- Invoice / refund history notes and audit summaries now write money in the order's currency ("Invoice INV-… created; payment of ৳1,250.00 recorded. Paid with bKash through SSLCommerz.", "Credit memo CM-… created; ৳250.00 refunded through SSLCommerz.").

### SSLCommerz routes
- **Return trip** `POST /api/v1/payments/sslcommerz/return` (no sign-in, `throttle:sslcommerz`; JSON or form):
  `{ result: "success"|"fail"|"cancel", tran_id: "<number>-<n>", val_id?: string (≤100), status?: string, value_a?: string }` (`status` and `value_a` are accepted but never used for decisions)
  → **200** `{ data: { order_number: "BN-100123"|null, result: "<outcome>", confirmation: "success"|"failed"|"cancelled" } }`. Redirect to `/order-confirmation/<order_number>?payment=<confirmation>&provider=sslcommerz`.
  Outcomes: `paid`, `already_paid`, `review`, `pending` (SSLCommerz unreachable for validation; the IPN / expiry job / Check payment settles it) → `success`; `failed` (result fail), `invalid` (no val_id, or validation not VALID/VALIDATED), `mismatch` (amount ≠ amount due to the cent, currency ≠ order currency, or tran_id not one of this order's attempts), `cancelled_order` → `failed`; `cancelled` (result cancel) → `cancelled`; `unknown_order` → `failed` with `order_number: null`. **422** only when `result` isn't one of the three or `tran_id` doesn't look like `<something>-<digits>` (≤64). The posted status is **never** trusted: `success` validates `val_id` (`GET {api}/validator/api/validationserverAPI.php?val_id=&store_id=&store_passwd=&format=json&v=1`) before anything is recorded. fail/cancel add one staff history note per attempt+result (repeats are silent) and call nothing.
- **IPN** `POST /api/v1/payments/sslcommerz/ipn` (no sign-in, `throttle:sslcommerz`; SSLCommerz's form body unchanged, JSON also accepted): → **200** `{ received: true, result }` with `paid`, `already_paid`, `review`, `duplicate`, `noted`, `ignored`, `invalid`, `mismatch`, `cancelled_order`, `unknown_order`; **400** `{ message: "Invalid SSLCommerz notification." }` (no/too long `tran_id`, VALID without `val_id`, or a `verify_sign`+`verify_key` that don't match — checked only when present); **503** `{ message: "SSLCommerz could not be reached to validate the notification." }` (SSLCommerz retries). VALID/VALIDATED → validated with the validation API (the posted amount/status are ignored), idempotent through `payment_events` (provider `sslcommerz`, id = `val_id`). FAILED/CANCELLED/EXPIRED/UNATTEMPTED → one staff note "SSLCommerz reported attempt BN-…-1 as FAILED." (id `<tran_id>:<STATUS>`), nothing else.
- **Pay now** (`POST /api/v1/orders/{number}/pay`) and the admin payment link (`POST /api/admin/v1/orders/{number}/payment-link`, `orders.edit`, audited `order.payment_link_created`) work for SSLCommerz orders: **every call starts a new attempt** (`tran_id` suffix +1; no reuse of an open page), answer as Stripe/PayPal (`payment: { provider: "sslcommerz", url, expires_at, … }`, or `url: null` + `error`). The order tracks the page for 3 hours (storefront) / 24 hours (staff link). An older attempt's success is still accepted (validated, amount matching); once paid, a later attempt's payment → `already_paid` + "Order … was paid again through SSLCommerz" notification (refund it in the panel).
- **Check payment** `POST /api/admin/v1/orders/{number}/payment/check` (`orders.edit`) → **200** `{ data: AdminOrderResource, result: { found: bool, status, message } }`. Asks the query API (`GET {api}/validator/api/merchantTransIDvalidationAPI.php?tran_id=…`) about every attempt, newest first, and records the first VALID/VALIDATED one. `status`: `paid` ("Payment found and recorded: ৳1,250.00 (BKASH-BKash). The order was invoiced."), `review`, `already_paid`, `mismatch`, `cancelled_order`, `not_found` ("SSLCommerz has no completed payment for this order (2 attempts checked)."), `unreachable` (found false, SSLCommerz's error as message). **422** `errors.order`: "This order isn't paid through SSLCommerz." / "SSLCommerz payments are not set up (…)." / "No SSLCommerz payment was started for this order yet." / "This order has already been paid.". 404 for unknown orders. Audited `order.payment_checked`.
- **Expiry**: `php artisan buynest:payments:expire-sslcommerz` (scheduled every 5 minutes, without overlapping, one server). Unpaid `pending_payment` SSLCommerz orders whose `payment_expires_at` passed: query every attempt first (VALID → recorded instead: `paid`/`review`/…); SSLCommerz unreachable → `skipped` (next run); else cancelled (stock back once, points and gift card returned, coupon use released) with "Payment not completed" email. Output e.g. "Expired SSLCommerz payments: paid 1, cancelled 1.".
- **Refunds**: a credit memo on an order paid through SSLCommerz refunds through SSLCommerz first: `GET {api}/validator/api/merchantTransIDvalidationAPI.php?bank_tran_id=&refund_amount=&refund_remarks=Refund for order BN-…&refe_id=<order number>-CM<n>&format=json` (n = the order's memo count + 1; the memo number doesn't exist before it's saved). `status: "success"` or `"processing"` → memo saved with `refund_reference` = `refund_ref_id` (processing adds a staff note "SSLCommerz accepted the refund of ৳250.00 and is still processing it (refund RF-…)."); anything else → 422 `errors.refund` "SSLCommerz refused the refund: <errorReason>." and nothing is saved.

### Emails and PDFs
- Templates write money variables as `${{ order_total }}` (also `invoice_amount`, `refund_total`, `amount`, `cart_subtotal`): that now means "this amount with the email's currency symbol" — `$59.97` / `৳1,250.00` — so saved custom templates keep working. Written without the `$`, the variable is the plain number. The order's emails use the order's currency, gift card emails the card's. Items/totals tables use the same format (`৳1,250.00`). Sample values (admin preview) use the store currency.
- PDFs format in the order's currency. **DejaVu Sans has no ৳ (U+09F3)**, contrary to the contract's assumption: Noto Sans Bengali Regular/Bold (OFL, `backend/resources/fonts/`, with `OFL.txt`) is registered from the local disk and follows DejaVu Sans in the font list; dompdf 3 takes each character from the first font that has it. The dompdf font cache lives in `storage/framework/cache/dompdf-fonts`. A test checks the subset font is embedded. The payment line reads "<method label> (bKash)" for SSLCommerz, "(PayPal)", "(Stripe)".

### `buynest:currency:convert` (§2, see `docs/CURRENCY.md`)
`php artisan buynest:currency:convert BDT --rate=110 [--dry-run] [--round=1|5|10|0.01] [--from=USD]`
- Converts (× rate, rounded to `--round`, halves up): products `price`, gift card products' `gift_card_amounts` / `gift_card_min_amount` / `gift_card_max_amount` (deleted products too), variant `price` (non-null), catalog rules with `action=fixed` (`amount`), coupons/cart rules (`value` when `type=fixed`, `min_subtotal`), shipping rates (`price`, `min_subtotal`, `max_subtotal`), settings `standard_price`, `express_price`, `next_day_price`, `free_shipping_threshold` (written even when they were defaults) and `rewards_point_value` (× rate, 4 decimals, not stepped).
- Also: gift cards in the old currency with a balance > 0 → `balance` and `initial_balance` × rate **to the paisa** (no customer loses money to rounding), `currency` = target, a 0.00 transaction "Currency changed: 25.50 USD → 2805.00 BDT (rate 110)."; `customer_carts.subtotal` (to the paisa); display currency rates ÷ rate (8 decimals), and a display row equal to the target is disabled. Spent cards, orders, items, invoices, credit memos, payments, history: untouched.
- Refuses (exit 1): `BUYNEST_CURRENCY` ≠ target ("Set BUYNEST_CURRENCY=BDT first …"), a previous conversion to the same target ("already converted to BDT once …"), from = to. Bad `--rate`/`--round` → exit 2. `--from` defaults to the last conversion's target, else `USD`. One transaction (dry run = the same work rolled back, so its counts are real; prints counts and up to 3 before/after examples per kind). Records `currency_conversions` (`actor: cli`) and audit `currency.converted` ("Store prices converted USD → BDT at 110 (rounded to 1.00).", subject `currency_conversion`).

### Choices the contract left open
- `STRIPE_CURRENCY`: removed, not "used when set".
- SSLCommerz `manual` mode accepts orders (they wait for staff); `unavailable` refuses them.
- Each Pay now / payment link is a new attempt (never reuses an open SSLCommerz page).
- `refe_id` = `<order number>-CM<n>` (the memo number isn't known before the refund is accepted).
- Risk hold uses the existing `payment_problem` notification type (no new type), and is approved with the normal invoice action.
- Check payment and the expiry job trust the authenticated query API's transaction list (no second validation call).
- The return endpoint doesn't require the shared key beyond what `BUYNEST_REQUIRE_BFF_KEY` already enforces in production (nothing is trusted from it).

### Store currency (§1)

Display currencies stay relative to the store currency (a BDT store can offer USD for display).
- Order money uses the order's `currency`: `OrderDetailsView` (items, totals, invoices, refunds, gift card and points lines), `OrdersPage`, `InvoicePage` (the invoice's `currency`), return refunds (`credit_memo.currency`, else the order's), gift card balance (the card's `currency`). Without one: the store currency.

### BFF (`frontend/server`)
- Shop answers: orders carry `currency` (3 letters, upper-cased; anything else dropped); invoice and credit memo summaries and the printable invoice carry `currency`; `payment` adds `methodLabel` (`method_label`) and `cardType` (`card_type`) when present. Staff-only keys (`reference`, `sslcommerz`) never reach the storefront.
- `POST /api/payments/sslcommerz/return/{success|fail|cancel}` (`paymentsApi.js`): reads the posted form (urlencoded, or multipart), keeps only `tran_id`, `val_id`, `status`, `value_a` (each pattern-checked), forwards `{ result, tran_id, val_id, status, value_a }` as JSON to `POST /api/v1/payments/sslcommerz/return` with the shared key (no cookies read, no `Authorization`), and answers **303** with a relative `Location: /order-confirmation/<number>?payment=<confirmation>&provider=sslcommerz` (`Cache-Control: no-store`, `Referrer-Policy: no-referrer`). `confirmation` comes from the API; a 422 on `success` → `failed`; the API unreachable → the route's own result (`success` → the page polls; the IPN settles it). Order number: the API's `order_number`, else `value_a`, else `tran_id` before its attempt suffix; none, or `result: unknown_order` → `Location: /`. Nothing to forward (no valid `tran_id`/`value_a`) → no API call. 405 for other methods, 404 for other results, 413 over 64 KB. It sits before the cross-site check in `server/api.js` (the POST comes from SSLCommerz's domain).
- `POST /api/payments/sslcommerz/ipn` → raw bytes and content type (default `application/x-www-form-urlencoded`) to `POST /api/v1/payments/sslcommerz/ipn` with the shared key, 25 s timeout; status passed through (400/503 so SSLCommerz retries), body `{ message }` or `{ received }`; 502 when the API is down.
- Hosting: no new function files. Vercel's `api/payments/[...path].js` (catch-all, `POST`) and Netlify's `/api/payments/*` already cover both paths at any depth; `npm run dev`/`preview` serve them through `vite.config.js`. Register in SSLCommerz: `success_url`/`fail_url`/`cancel_url` = `https://<store>/api/payments/sslcommerz/return/success|fail|cancel`, `ipn_url` = `https://<store>/api/payments/sslcommerz/ipn`.
