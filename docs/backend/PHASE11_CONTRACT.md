# Phase 11 contract: saved wishlists, comparison, linked products, reward points, display currencies

**Status: built (2026-11-18).** Choices made where this page left something open are in the implementation notes (backend, storefront, admin) at the end.

Free features only: nothing here needs a paid account or an outside service. Keeps the conventions of phases 1 to 10 (`snake_case`, money as 2-decimal strings, `{ data }`, Laravel 422 errors, `can.admin:<key>` on every admin route, audit entries for admin changes, the sign-in service (BFF) in front of every browser call, the API locked to the store in production, the DummyJSON demo mode unchanged: in demo mode every new feature either works locally in the browser or is hidden).

## 1. Wishlist saved to the account, and sharing

Today the wishlist lives only in the browser (`WishlistProvider`, local storage per user id). Signed-in customers on the Laravel backend now keep it on the server, so it follows them across devices.

- `wishlist_items`: `id, customer_id, product_id, product_variant_id null, note null (max 255), created_at`; unique `(customer_id, product_id, product_variant_id)`; cascade on customer delete; product delete removes the row.
- Customer routes (signed in, `throttle:api`):
  - `GET /api/v1/me/wishlist` → `{ data: [{ id, product (the normal storefront product card: id, name, slug, price, final price after catalog rules, image + srcset, rating, stock status), variant (id, label) | null, note, added_at }] }`. Products that are no longer visible are left out (not deleted).
  - `POST /api/v1/me/wishlist { product_id, variant_id? , note? }` → 201 with the item (adding an existing one answers 200 with it, no duplicate). Max 100 items (422 `wishlist_full`).
  - `PATCH /api/v1/me/wishlist/{id} { note }`, `DELETE /api/v1/me/wishlist/{id}`.
  - `POST /api/v1/me/wishlist/merge { items: [{ product_id, variant_id? }] }` merges the guest list once after sign-in (like saved carts in phase 7); unknown or hidden products are skipped and reported in `meta.skipped`.
- **Sharing:** `POST /api/v1/me/wishlist/share` creates (or returns) a share link token (32 random URL-safe chars; stored as a SHA-256 hash on `customers.wishlist_share_hash`, plus `wishlist_shared_at`); the plain token is only returned at creation and on regenerate (`POST .../share { regenerate: true }`). `DELETE /api/v1/me/wishlist/share` turns sharing off. `GET /api/v1/me/wishlist` adds `meta.shared: bool`.
- Public `GET /api/v1/wishlists/{token}` (rate-limited) → `{ data: { owner_first_name, items: [product cards + variant label + note] } }`; 404 for unknown/revoked tokens. Never exposes email, last name, ids of the customer.
- Storefront: on the Laravel backend a signed-in wishlist reads and writes through these routes (optimistic update, rolled back on error); guests keep the browser list, merged on sign-in. Wishlist page gets "Share my wishlist" (copy link, regenerate, stop sharing) and per-item note. New page `/wishlist/shared/:token` with "Add to cart" per item and "Add all to cart". Demo mode: unchanged browser-only behaviour, no share button.
- Admin: customer page gets a **Wishlist** tab (`customers.view`): product, variant, note, added date. Reports get **Most wished-for products** (`reports.view`): product, number of customers, in stock?, with date-range filter like the other reports.

## 2. Product specifications and comparison

- New product column `specifications` (json, nullable): ordered list of `{ label (max 60), value (max 255) }`, max 40 rows, labels unique per product (case-insensitive). Returned by the storefront product detail and the admin product resource; editable in the admin product form ("Specifications" section: add/remove/reorder rows); CSV import/export column `specifications` as `Label: Value | Label: Value`.
- `GET /api/v1/products/compare?ids=1,2,3,4` (2–4 ids, visible products only, unknown ids skipped) → `{ data: [product detail subset: id, name, slug, image, price, final price, rating, review count, brand, category, stock status, weight, options (names and values), specifications, short description] }`.
- Storefront: "Compare" toggle on product cards and the product page; the compare list (max 4, one per product, kept in local storage for the browser, works for guests and in demo mode) shows as a small sticky bar ("Compare (3)" · Clear) that links to `/compare`. The compare page is a table with a column per product (image, name, price, rating, stock, brand, category, weight, options, then the union of specification labels in the order first seen; missing values show "—"), a "Highlight differences" toggle, Remove and Add to cart per column. Adding a 5th shows a message instead. Accessible: a real `<table>` with row headers (`<th scope="row">`), scrolls sideways on phones with a focusable region. Demo mode builds the table from DummyJSON products (no specifications rows).
- Product page shows a "Specifications" table when the product has any.

## 3. Related products, up-sells and cross-sells (Magento product links)

- `product_links`: `id, product_id, linked_product_id, type (related|upsell|crosssell), position`; unique `(product_id, linked_product_id, type)`; no self-links; cascade on delete of either product.
- Admin product form, new section **Related products, up-sells and cross-sells** (`products.edit`): for each type a list with a product search picker (by name or SKU, existing products search route), remove, reorder; max 20 per type. Saved with the product (`links: { related: [ids], upsell: [ids], crosssell: [ids] }` on create/update; omitted = unchanged). The admin product resource returns `links` with `{ id, name, sku, image, status }` per entry. CSV export/import columns `related_skus`, `upsell_skus`, `crosssell_skus` (`|`-separated SKUs; unknown SKUs reported as row warnings). "Duplicate product" copies the links.
- Storefront product detail answers `related` (max 8) and `upsells` (max 4): visible, in-stock-first, product cards. When a product has **no** related links, `related` falls back to the current automatic choice (same category, best rated) so the page never loses the section; `meta`-free, just the list.
- `POST /api/v1/cart/validate` answers `cross_sells` (max 4): cross-sell links of the cart's products, excluding products already in the cart, visible only, ordered by how many cart items point to them, then position.
- Storefront: product page shows **"You may also like"** (up-sells) above the reviews and **"Related products"** below; cart page shows **"Customers also bought"** (cross-sells) with Add to cart. Demo mode keeps today's automatic related products and shows no up-sell or cross-sell section.

## 4. Reward points (loyalty)

Settings (`settings.edit`, Settings → **Reward points**), stored like other settings:
`rewards.enabled` (default false), `rewards.earn_rate` (points per 1.00 of eligible spend, default 1), `rewards.point_value` (money per point when spending, default 0.01), `rewards.min_redeem` (default 100), `rewards.max_percent` (max share of the order total that points may pay, 1–100, default 50), `rewards.signup_bonus` (default 0), `rewards.review_bonus` (default 0).

- `customers.reward_points` (int, default 0: the balance) and `reward_transactions`: `id, customer_id, points (signed int), balance_after, type (earn|spend|cancel_return|refund_return|refund_reverse|signup|review|adjust), order_id null, credit_memo_id null, review_id null, admin_id null, note null, created_at`. Every balance change goes through one service (`App\Services\RewardPoints`) with the customer row locked (`lockForUpdate`); the balance never goes below 0.
- **Earning:** when an order of a signed-in customer is **invoiced** (paid), it earns `floor(eligible × earn_rate)` points, where eligible = item subtotal after discounts, excluding shipping, tax, gift card products, and the part paid with points. Once per order (unique earn per order). Orders store `reward_points_earned` (int, null until invoiced). Signup bonus on account creation (after email verification for self-registered accounts), review bonus when a review is **approved** (once per customer and product). Nothing is earned while `rewards.enabled` is false.
- **Spending:** checkout and cart validation accept `reward_points` (int ≥ 0) for signed-in customers when enabled. Rules: ≤ balance, ≥ `min_redeem` (unless 0), value = points × point_value, rounded to cents, ≤ `max_percent` of the grand total (after discounts, shipping and tax); the API answers 422 `reward_points` with a clear message otherwise. Applied **after** tax and **before** a gift card (order of payment: points → gift card → payment method). Orders store `reward_points_spent` (int) and `reward_points_amount` (money). If points and/or a gift card cover the whole total, no other payment is needed (same path as a fully covered gift card order; `payment_method` value accepted the same way).
- Cart validation answers `rewards: { enabled, balance, point_value, min_redeem, max_points (usable on this cart), earn_estimate }` for signed-in customers (`null` for guests or when off).
- **Cancel** an unplaced/unpaid order (customer cancel, expiry, admin cancel) → spent points come back (`cancel_return`). **Refund** (credit memo) → spent points come back in proportion to the refunded share (`refund_return`), and earned points are taken back in proportion (`refund_reverse`, never below 0; the shortfall is noted). Refunds settle points first, then gift card, then the payment method; the admin refund dialog shows the split.
- Customer: `GET /api/v1/me/rewards` → `{ data: { balance, value (money), transactions: paginated history } }`.
- Admin (`customers.view` to see, new `rewards.manage` to adjust): customer page **Reward points** tab (balance, history, "Adjust balance" with signed points and a required note, audited); order page shows points spent/earned; customers grid optional column "Points". Reports: points issued / spent / outstanding liability (money) by period (`reports.view`).
- Storefront (Laravel mode, when enabled): account **Reward points** page (balance, its money value, history); checkout "Use reward points" (input with max, "Use all"), summary line "Reward points (500 pts) −$5.00"; product page "Earn about N points" for signed-in shoppers; order details show points spent and earned. Demo mode and disabled: nothing shown.
- Emails: the order confirmation shows points spent; the invoice email shows points earned (template variables `reward_points_spent`, `reward_points_earned`; defaults updated in `EmailTemplateCatalog`).

## 5. Display currencies (e.g. BDT)

The store keeps charging in its base currency (USD); shoppers can choose to **see** prices in another currency.

- `currency_rates`: `id, code (ISO 4217, unique), symbol (max 5), rate (decimal 18,8: units per 1 base), decimals (0–3), enabled, position, updated_at`. Rates are typed in by staff (no paid rate service). Settings → **Currencies** (`settings.edit`): add/edit/disable/reorder, with "last updated" shown and a warning when a rate is older than 30 days. Seed BDT (`৳`, 2 decimals, rate 0, disabled) and EUR (`€`, disabled) as examples.
- `GET /api/v1/store` adds `currencies: { base: "USD", display: [{ code, symbol, rate, decimals }] }` (enabled ones with a rate > 0 only).
- Storefront: a currency picker in the header (only when at least one display currency exists; choice kept in local storage). Every shopper-facing price goes through one formatter that converts and rounds for display; base currency is the default so nothing changes until a shopper chooses. When a non-base currency is shown, cart and checkout show "Prices in BDT are approximate. You'll be charged $X.XX USD." and the order summary / emails / invoices / PDFs always show the charged base amounts. Demo mode: the picker is hidden.
- Admin always shows base currency.

## 6. Recently viewed products

- Storefront only (no API): the last 12 products viewed in this browser (local storage, per browser, newest first, de-duplicated), shown as a "Recently viewed" row on the product page (excluding the current product) and the home page; "Clear" link. Works in demo mode too. Not stored on the server, so it isn't part of the data export.

### §1 Wishlist
Item shape (customer and admin):
```
{ id, product: <card>, variant: { id, label } | null, note: string|null, added_at: ISO }
```
Newest first. Products that aren't for sale (draft/archived/deleted/hidden category) are left out of every answer (rows kept). Only product visibility filters rows; the variant is shown with its label even if it was switched off since.
- `GET /api/v1/me/wishlist` → `{ data: [item…], meta: { shared: bool, shared_at: ISO|null, count: int (visible items), limit: 100 } }`.
- `POST /api/v1/me/wishlist { product_id, variant_id?, note? }` → **201** `{ data: item }`; already there → **200** `{ data: item }` (a `note` sent with it replaces the note). Errors: product missing/not for sale → 422 `errors.product_id` "This product isn't available."; variant not of this product / inactive → 422 `errors.variant_id` "This option isn't available."; 100 items → **422** `{ message: "Your wishlist is full (100 items). Remove something to add more.", code: "wishlist_full", errors: { product_id: [same] } }`. The limit counts every row (also hidden products).
- `PATCH /api/v1/me/wishlist/{id} { note }` (null/"" clears) → `{ data: item }`; `DELETE /api/v1/me/wishlist/{id}` → 204. Someone else's / unknown id → 404 `{ message: "Wishlist item not found." }`.
- `POST /api/v1/me/wishlist/merge { items: [{ product_id, variant_id? }] }` (max 100) → 200 `{ data: [item…] (the full list), meta: { shared, shared_at, count, limit, added: int, skipped: [{ product_id, variant_id, reason: "unavailable" | "full" }] } }`. Existing rows are not duplicated (not counted as added, not skipped).
- `POST /api/v1/me/wishlist/share { regenerate?: bool }` → new link (first time, or `regenerate: true`) **201** `{ data: { shared: true, token: "<32 chars>", shared_at } }`; already shared without regenerate → **200** `{ data: { shared: true, token: null, shared_at } }` (the plain token can't be shown again: regenerate to get a new one). Tokens are 32 chars `A–Z a–z 0–9` (the public route also accepts `-`/`_` so the format can change later). The storefront link is `/wishlist/shared/{token}`.
- `DELETE /api/v1/me/wishlist/share` → 204 (old links answer 404).
- Public `GET /api/v1/wishlists/{token}` (`throttle:wishlist-share`, 60/min per IP) → `{ data: { owner_first_name, items: [{ product: <card>, variant: { id, label } | null, note, added_at }] } }` (no item ids, no customer data). Unknown/revoked → 404 `{ message: "This wishlist isn't shared any more." }`.
- Admin `GET /api/admin/v1/customers/{id}/wishlist` (`customers.view`) → `{ data: [{ id, product: { id, name, sku, thumbnail_url, status, deleted: bool }, variant: { id, label } | null, note, added_at }] }` (every row, hidden products included so staff see them), `meta: { shared: bool, shared_at }`.
- Admin report `GET /api/admin/v1/reports/wishlist?from=&to=&limit=` (`reports.view`; same date rules as the other reports: rows **added** within the dates; `limit` default 10, max 100) → `{ data: [{ product_id, name, sku, thumbnail_url, customers: int, in_stock: bool, availability }], meta: { from, to } }`, most customers first.
- Deleting a product (soft delete in the admin) deletes its wishlist rows and its links (both directions).

### §2 Specifications and comparison
- `specifications`: always an array (`[]` when none) on the storefront detail (`GET /products/{id}`), the compare answer, and the admin product resource (list and detail).
- Admin create/update: `specifications: [{ label, value }] | null` (null or `[]` clears; omitted = unchanged). Labels/values are trimmed. Errors: `specifications` ("At most 40 specification rows."), `specifications.N.label` (required, max 60, "This label is used twice." — case-insensitive), `specifications.N.value` (required, max 255).
- `GET /api/v1/products/compare?ids=1,2,3` → `{ data: [ <card> + { description_short: string|null (plain text, max 200 chars), options: [{ name, values: [string] }], specifications: [...] } ] }`, in the order of `ids`; unknown/hidden ids are skipped (answer can have < 2). Fewer than 2 or more than 4 distinct ids (or non-numbers) → 422 `errors.ids` "Choose 2 to 4 products to compare.". Image = `thumbnail_url`/`thumbnail_variants`, final price = `sale_price`, stock status = `availability`.

### §3 Product links
- Admin create/update `links: { related?: [ids], upsell?: [ids], crosssell?: [ids] }` — each list replaces that type in the given order (position 0..n); a type left out is unchanged; `links` omitted = all unchanged. Errors: `links.related` (max 20 "At most 20 products per list."), `links.related.N` ("This product doesn't exist." for unknown/deleted ids, "A product can't be linked to itself.", distinct "This product is listed twice."). Same for `upsell`/`crosssell`.
- Admin product resource **detail** (`GET/POST/PATCH /products…`) adds `links: { related: [entry], upsell: [entry], crosssell: [entry] }`, entry `{ id, name, sku, image (thumbnail_url), status }` (deleted linked products are left out). Lists don't include `links`.
- **Duplicate:** new `POST /api/admin/v1/products/{id}/duplicate` (`products.edit`) → **201** admin detail of the copy: name "<name> (copy)", new slug, SKU "<sku>-COPY" (then -COPY-2, …), status `draft`, same category/brand/price/discount/stock/min qty/description/SEO/tags/weight/type/gift card settings/specifications/links, and the gallery's external image URLs (uploaded files are not copied). Options and variants are **not** copied. Audited `product.duplicated`.
- CSV: export header adds `specifications,related_skus,upsell_skus,crosssell_skus` at the end (`Label: Value | Label: Value`, `|`-separated SKUs). Import accepts these columns (an empty cell or a missing column = unchanged; there is no way to clear them by CSV). A bad specifications cell (no `:`, label > 60, value > 255, > 40 rows, duplicate label) is a row error. Link SKUs may name products of the same file. Unknown SKUs and the product's own SKU are skipped and reported in the new `data.warnings: [{ row, column, message }]` (always present, `[]` when none); more than 20 per type is a row error.
- Storefront detail `GET /api/v1/products/{id}` adds `related: [<card>…]` (max 8) and `upsells: [<card>…]` (max 4): visible only, in stock first, then link position. With **no** related links (none at all, or none visible) `related` = up to 8 visible products of the same category, best rated first (`rating_average` desc, then id), excluding the product itself.
- `POST /api/v1/cart/validate` adds `cross_sells: [<card>…]` (max 4, `[]` when none): cross-sell links of the charged cart products, not already in the cart, visible, ordered by the number of cart lines linking to them (desc), then the smallest position, then id. Not added to admin quote.

### §4 Reward points
Settings (`GET/PATCH /api/admin/v1/settings`) group **`rewards`**: `{ enabled: bool, earn_rate: "1.00", point_value: "0.0100", min_redeem: int, max_percent: int, signup_bonus: int, review_bonus: int }`. Validation: `earn_rate` numeric 0–1000 (2 decimals, returned as a "0.00" string), `point_value` numeric 0.0001–100 (4 decimals, returned as a "0.0000" string), `min_redeem` 0–1,000,000, `max_percent` 1–100, bonuses 0–1,000,000. (Stored as settings keys `rewards_enabled` etc.; the API uses the short names above.)

`GET /api/v1/store` adds `rewards: { enabled, earn_rate: "1.00", point_value: "0.0100", min_redeem }` (the product page's "Earn about N points" = floor(final price × earn_rate)) and `currencies` (§5).

Money value of points: `round(points × point_value, 2)` (halves up).

**cart/validate** request adds `reward_points` (int ≥ 0, null). Answer adds:
```
rewards: null | { enabled: true, balance: int, point_value: "0.0100", min_redeem: int, max_points: int, earn_estimate: int,
                  applied_points: int, applied_amount: "0.00" },
reward_points_error: string | null,
totals: { …, reward_points: "0.00", gift_card, amount_due }   // amount_due = total − reward_points − gift_card
```
`rewards` is null for guests or when rewards are off; a `reward_points` > 0 sent then is not applied and `reward_points_error` says "Sign in to use reward points." / "Reward points aren't available right now." (cart/validate still answers 200). `max_points` = min(balance, the most points whose value ≤ min(max_percent % of the grand total, grand total − gift card lines)); 0 when that is below `min_redeem`. `earn_estimate` = floor((merchandise after discounts − points value) × earn_rate), gift card lines excluded. Errors (points not applied, everything else priced; numbers formatted with thousands separators, e.g. "1,000"): "You have only N points." / "Use at least N points." / "Reward points can't be used on this order." (max_points is 0) / "You can use at most N points on this order." Points are never applied to gift card lines.

**Checkout** `POST /api/v1/orders` accepts `reward_points` (signed-in only). Errors → 422 `errors.reward_points`: the three above, plus "Sign in to use reward points." (guest with points > 0) and "Reward points aren't available right now." (disabled with points > 0). Points are taken at placement (customer row locked) → transaction `spend`. Payment order: points → gift card → payment method. When points (alone or with a gift card) cover the whole total, the order is placed **paid** at once (invoice note "Paid with reward points (500 pts)." / "Paid with gift card ••••ABCD and reward points (500 pts)."), `payment_method` becomes `"gift_card"` when a card is involved, else **`"reward_points"`** (also accepted as an input value, like `gift_card`; sent but not covered → 422 `payment_method` "Your reward points don't cover the whole total. Choose how to pay the rest."), `payment.provider` = `"gift_card"` / `"reward_points"`. Stripe/PayPal charge `amount_due` only. Admin "Create order" does not take reward points.

**Orders** (customer and admin `OrderResource`, invoices): `totals.reward_points: "5.00"`, `totals.amount_due` (minus points), and top-level `reward_points: { spent: int, amount: "5.00", earned: int|null } | null` (null when nothing was spent and nothing earned). `payment_method: "reward_points"` is labelled "Reward points".

**Earning:** at invoice (every invoice path: staff invoice, PATCH paid, bulk, Stripe/PayPal, full cover) when the order has a customer and rewards are on: floor((Σ non-gift-card line totals − discount_total − reward_points_amount) × earn_rate) → `earn` (once per order) and `orders.reward_points_earned` (also when 0). Guests/off → stays null. Signup bonus: on first email verification of a self-registered account (verify-email, or a password reset that verifies it) and when staff create an account; once per customer. Review bonus: when a review becomes approved (auto-approved on create, or staff approve), once per customer and product.

**Cancel** (customer, Stripe/PayPal expiry, staff, bulk): unreturned spent points come back → `cancel_return`.

**Refunds** (credit memo): split **points first, then gift card, then the payment method**. `GET /orders/{number}/refundable` adds `reward_points_refundable: "0.00"` (money still returnable as points) and `reward_points: { spent, earned, reversed }`. Credit memo answers add `reward_points_refund: "0.00"` (money returned as points), `reward_points_returned: int`, `reward_points_reversed: int`; `other_refund` = total − gift_card_refund − reward_points_refund. Points returned for a memo = round(spent × cumulative points-refund money ÷ reward_points_amount) − already returned (`refund_return`). Earned points taken back = round(earned × cumulative refund total ÷ grand_total) − round(earned × previous refund total ÷ grand_total), capped at the balance (`refund_reverse`; the shortfall is written in the transaction note and the order history).

**Customer:** `GET /api/v1/me/rewards?page=&per_page=` (default 20, max 100) → `{ data: { enabled: bool, balance: int, value: "5.00", point_value: "0.0100", transactions: [tx…] }, links, meta }` (pagination of the transactions, Laravel style). Customer tx: `{ id, points (signed), balance_after, type, order_number|null, note, created_at }`. `GET /api/v1/me` (`CustomerResource`) adds `reward_points: int`.

**Admin:** customer list and profile add `reward_points: int` (customers grid "Points"). `GET /api/admin/v1/customers/{id}/rewards?page=` (`customers.view`) → same shape as the customer's, tx adds `admin_name`, `credit_memo_number`. `POST /api/admin/v1/customers/{id}/rewards/adjust { points (signed int, ≠ 0, |points| ≤ 1,000,000), note (required, max 255) }` (`rewards.manage`) → 200 `{ data: { balance, value, transaction: tx } }`; below 0 → 422 `errors.points` "The balance can't go below 0 (it is N points)."; audited `reward_points.adjusted`. Works even while rewards are disabled.
Report `GET /api/admin/v1/reports/rewards?from=&to=&group_by=day|week|month` (`reports.view`) → `{ data: { totals: { issued: int, spent: int, returned: int, reversed: int, adjusted: int }, series: [{ period, issued, spent }], outstanding_points: int, outstanding_value: "0.00", point_value }, meta: { from, to, group_by } }`. issued = earn + signup + review; spent = |spend|; returned = cancel_return + refund_return; reversed = |refund_reverse|; adjusted = the net sum of `adjust` rows (signed). Spend/issue rows are counted by their created_at date. Outstanding = Σ balances now × point_value.

**Emails:** `order_confirmation` gets block variable `reward_points_spent` (a paragraph "You used 500 reward points ($5.00) on this order.", empty without) and a "Reward points (500 pts) −$5.00" totals row; `invoice` gets block variable `reward_points_earned` ("You earned 120 reward points with this order.", empty without). Both added to the default bodies.

### §5 Currencies
Rate row: `{ id, code, symbol, rate: "110.00000000", decimals, enabled, position, updated_at, stale: bool (updated more than 30 days ago) }`.
- `GET /api/admin/v1/currencies` (`settings.view`) → `{ data: [row…], meta: { base: "USD" } }` (position, id).
- `POST /api/admin/v1/currencies { code, symbol, rate, decimals?, enabled?, position? }` (`settings.edit`) → 201 `{ data: row }`. `code` 3 letters A–Z (upper-cased), unique, not the base currency; `symbol` 1–5 chars; `rate` 0–1,000,000,000, max 8 decimals; `decimals` 0–3 (default 2); enabled with rate 0 → 422 `errors.rate` "Enter a rate before turning this currency on.".
- `PATCH /api/admin/v1/currencies/{id}` (same fields, optional) → `{ data: row }`; `DELETE /api/admin/v1/currencies/{id}` → 204; `POST /api/admin/v1/currencies/reorder { ids: [...] }` (every row) → `{ data: [row…] }`. All audited `currency.*`.
- `GET /api/v1/store` → `currencies: { base: "USD", display: [{ code, symbol, rate: "110.00000000", decimals }] }` (enabled and rate > 0, by position).

### Permissions
`rewards.manage` ("Adjust customers' reward point balances") in the Customers group.

### Data export / deletion
`GET /api/v1/me/export` adds `wishlist: [{ product, variant, note, added_at }]` (every row, by product name) and `reward_transactions: [{ points, balance_after, type, order_number, note, created_at }]`, plus `reward_points: int` in `profile`. Deleting an account removes wishlist rows and reward transactions (FK cascade).

### Storefront choices
- **Wishlist (§1)** — `context/WishlistProvider.jsx`.
