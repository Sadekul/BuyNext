# BuyNest browser checks

Real-browser checks for the storefront and the admin dashboard, driven through
[playwright-core](https://playwright.dev) using the Chrome already installed on
the machine (nothing extra is downloaded), plus [axe-core](https://github.com/dequelabs/axe-core)
accessibility audits. They complement the unit tests (`npm test` in `frontend/`
and `admin/`), which run without a browser.

## Run

```bash
cd e2e && npm install          # once

# Against the dev server (start everything first: ./dev.sh in the repository root)
npm test

# Against the production build (cd frontend && npm run build && npm run preview)
npm run test:prod

# One suite
node admin.mjs
BASE_URL=http://localhost:4173 node security.mjs
```

`CHROME_PATH` points at a different Chrome/Chromium binary (default `/usr/bin/google-chrome`).

Accounts: by default the checks use **BuyNest accounts** (`E2E_ACCOUNTS=laravel`), so the Laravel API must be running with its local demo accounts (`php artisan db:seed`) and its test inbox (`DEV_MAILBOX=true`), which `signup.mjs` reads the emailed codes from. Against a store set up with the DummyJSON demo users, run with `E2E_ACCOUNTS=dummyjson` (`signup.mjs` is then skipped). The catalog still comes from DummyJSON, so the checks need internet access.

With the BuyNest API the checks place real orders. `npm test` records every product's stock before the suites and puts it back afterwards; run single suites knowing they change stock (reset everything with `php artisan buynest:import-catalog --overwrite` in backend/).

`catalog.mjs` writes two reviews per run as the demo customer, and the API allows 10 review attempts per customer per hour, so after about five runs in an hour the review checks fail with "Too Many Attempts." Wait, or reset that limit locally: `php artisan tinker --execute='RateLimiter::clear(md5("reviews"."customer:1"));'` in backend/ (1 = the demo customer's id).

`marketing.mjs` also needs `php` on the machine: it backdates its own abandoned cart (`php artisan tinker`), clears the sitemap cache so its new product is listed at once, and removes its subscribers, notifications, and grid settings that have no delete endpoint. It sends a real newsletter only when every subscribed address is one of its own test addresses (otherwise that check fails and the send is skipped), and reads the `List-Unsubscribe` header from the test inbox (`/dev/mailbox/latest` includes `headers`).

`payments.mjs` changes no `.env` file: Laravel and Vite both let variables already set in the process environment win over `.env` / `.env.local`, so its own servers get `STRIPE_SECRET_KEY=sk_test_e2e`, `STRIPE_WEBHOOK_SECRET=whsec_e2e_local`, `STRIPE_API_URL=http://127.0.0.1:12111`, `STOREFRONT_URL=http://localhost:5180` (Laravel) and `BUYNEST_LARAVEL_URL=http://127.0.0.1:8010` (storefront), while the usual servers keep Stripe off. Both APIs use the dev database. It needs `php` and `openssl` (for a throwaway certificate: the storefront only follows `https` payment links), and ports 12111, 12112, 8010, and 5180 free; it refuses to start otherwise, and stops every process it started at the end, on failure, and on Ctrl+C.

`launch.mjs` needs `php` (it backdates a sign-in challenge to check expiry, counts emails in the test inbox, and removes stock alerts, backup files, and backup run records that have no delete endpoint), GD in PHP (for the resized photo copies), and `mysqldump` (Back up now). It never turns on two-step sign-in for the demo admin, whom every suite signs in as: while it turns "Require two-step sign-in" on, its own test Owner (with two-step) makes the API calls, and the setting is turned off again right after that check and once more at the end, even on failure. It reads the Laravel log (`backend/storage/logs/laravel.log`) for the browser error reports, which are written there when Sentry isn't set up. A run waits for up to two 30-second authenticator time steps (the API never accepts a code twice).

`extras.mjs` changes no `.env` file either: its API gets `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_MODE=sandbox`, `PAYPAL_WEBHOOK_ID`, `PAYPAL_API_URL=http://127.0.0.1:12121`, and `STOREFRONT_URL=http://localhost:5181` through its process environment, and its storefront `BUYNEST_LARAVEL_URL=http://127.0.0.1:8011` and `VITE_ANALYTICS=ga4`. The GA4 measurement id (`G-E2ETEST01`) is set through the admin settings API only for the consent checks and set back to empty at the end, even on failure; every browser request to `googletagmanager.com`, `google-analytics.com`, or `analytics.google.com` is answered inside Playwright (`context.route`) by a small fake `gtag.js` that reports each command to a fake `collect` address, which the suite records and inspects. The dev server has no CSP, so the CSP allowance is checked by calling `buildContentSecurityPolicy` from `frontend/vite.config.js` with and without `ga4`. It needs `php` (it reads the test inbox's emails to an address with `php artisan tinker`, since `/dev/mailbox/latest` only returns the newest, and removes webhook events, notifications, and the cached stand-in token), `openssl`, and ports 12121, 12122, 8011, and 5181 free. The test inbox doesn't record attachments, so the PDF attached to the invoice email is covered by the backend tests only.

`loyalty.mjs` starts no servers of its own and changes no `.env` file. It never touches the demo customers' wishlists or reward balances: every wishlist and points check uses its throwaway customer, which is deleted at the end (an open order blocks deleting a customer, so its paid orders are marked Shipped and Delivered through the API first; the guest order placed in BDT is cancelled). Reward points and BDT are read at the start and put back from what was read, even on failure.

`taka.mjs` changes no `.env` file either: its API gets `BUYNEST_CURRENCY=BDT`, `SSLCOMMERZ_STORE_ID`, `SSLCOMMERZ_STORE_PASSWORD`, `SSLCOMMERZ_MODE=sandbox`, `SSLCOMMERZ_API_URL=http://127.0.0.1:12131`, and `STOREFRONT_URL=http://localhost:5182` through its process environment, and its storefront `BUYNEST_LARAVEL_URL=http://127.0.0.1:8012`. The dev database stays in USD: its prices simply read as taka on the suite's servers. The two artisan commands (`buynest:payments:expire-sslcommerz`, after backdating two orders' payment windows with `php artisan tinker`, and `buynest:currency:convert … --dry-run`) run with that same environment, never against the usual API's settings, and the real conversion is never run. SSLCommerz is switched on in Settings → Checkout through the admin page and put back from what was read at the start, even on failure (in USD the usual API hides it anyway). It needs `php`, `openssl`, and ports 12131, 12132, 8012, and 5182 free. A USD gift card for the currency check is made through the usual API on :8000 (new cards take the store currency) and disabled at the end. The PDF's text is compressed, so the PDF check looks for the embedded Noto Sans Bengali font (the one that draws ৳) rather than the character itself.

`bangla.mjs` starts no servers of its own and changes no `.env` file. It never changes the demo customers' language: the language checks use its throwaway customer. Settings → General (default store language, Bangla digits) is changed through the admin page and put back from what was read at the start, even on failure. Email templates are only previewed. Products are only soft-deleted, so their Bangla texts are cleared through the API before they are removed, and the cleanup check counts the rows left in `product_translations` / `category_translations` with `php artisan tinker` (so it needs `php`). The PDF's text is read with `pdftotext` (poppler-utils) when it is installed; dompdf draws Bangla without shaping, so that text comes out in drawn order (`ইনভেয়স`) and the check looks for Bangla letters and digits rather than exact words.

`delivery.mjs` changes no `.env` file either: like `taka.mjs` its API gets `BUYNEST_CURRENCY=BDT`, `SSLCOMMERZ_STORE_ID`, `SSLCOMMERZ_STORE_PASSWORD`, `SSLCOMMERZ_MODE=sandbox`, `SSLCOMMERZ_API_URL=http://127.0.0.1:12141`, and `STOREFRONT_URL=http://localhost:5183` through its process environment (so the advance delivery charge can be turned on), and its storefront `BUYNEST_LARAVEL_URL=http://127.0.0.1:8013`; `buynest:payments:expire-sslcommerz` runs with the same environment after backdating one order's payment window with `php artisan tinker`. Both APIs use the dev database, so while it runs the usual store also has Bangladesh as its default country: Settings → Checkout (default country, payment methods, allowed countries) and Cash on delivery are read at the start and put back from what was read, even on failure, and the cleanup checks them, the table rates and the delivery zones (only read) against the start. It needs `php`, `openssl`, and ports 12141, 12142, 8013, and 5183 free. PDF text is read with `pdftotext` (poppler-utils) when it is installed; otherwise only the embedded Noto Sans Bengali font is checked.
